# Spec check 1

Inputs: `spec.md`, `checklists/requirements.md`, `sources/README.md`, `triage/011-layout-headers.md`, constitution
1.3.1, and, as they stand on the branch, `packages/tokens/src/source.ts`, `packages/styles/src/base.css` and
`packages/elements/README.md` ("Element conventions"). No earlier check exists. No browser probe was run (no
`node_modules` and no `OCELLE_CHROMIUM_PATH` in the container). Every token the spec names exists in `source.ts`
except the four eyebrow tokens FR-030 adds. The values used below come from `source.ts`.

| ID | Severity | Where | Finding | Fix |

| SPEC-1-01 | blocking | spec.md FR-025, US4-2; `source.ts` `shell-rail-width`, `size-rail-item`, `target-min` | A vertical rail is `--ocelle-shell-rail-width` (3.25rem, 52 px) wide with `--ocelle-space-2` (8 px) padding. That leaves 36 px for items. The library's rail item token `--ocelle-size-rail-item` is 2.5rem (40 px), and `--ocelle-target-min` is 44 px. The items #12's `ocelle-nav-item` is expected to supply (FR-027) cannot fit. They overflow the rail or get squeezed, and a focus ring around them gets clipped. US4-2 cannot pass with rail-sized items, and with no items of a stated size it checks nothing about fit. | Make the numbers agree. Either use inline padding that leaves at least `--ocelle-size-rail-item` (for example `--ocelle-space-1`, 52 − 8 = 44 px), or say the width is the content box. Then add a US4-2 outcome: a `--ocelle-size-rail-item` square item fits inside the vertical rail with no overflow, and its focus ring is not clipped. |
| SPEC-1-02 | blocking | spec.md FR-006, FR-012, FR-017, US1-8, US1-9 | FR-017 lets a section header's "own `size` attribute" win over a compact card. FR-006 says a value outside the list behaves as "the property's default", which FR-012 says is `"regular"`. The spec does not say what `size=""` or `size="bogus"` on a section header in a compact card gives: regular (the attribute is present and invalid, so it falls back to the default) or compact (no valid own size, so the card decides). It also does not say whether the default is an unset property (the README convention, `@default undefined`) or a `"regular"` value. If `"regular"` is set as the initial value and reflected, every section header gets `size="regular"` on upgrade and US1-8 can never hold. | State that the default means "no `size` attribute" (the property is not reflected until the page sets it). State what an empty or invalid `size` on a section header inside a compact card gives. Add a scenario for that case. |
| SPEC-1-03 | blocking | spec.md US1-13 | "No state or part is marked by colour alone" names no observable outcome, so no test can show it false. The one variant that only colour distinguishes is `inset` (a ground of `--ocelle-color-inset` instead of `--ocelle-color-sheet`, FR-016). In forced-colours mode both grounds become the system background, so an inset card looks the same as a regular one. The spec does not say whether that is acceptable. | Replace the phrase with concrete outcomes, for example: in forced colours an inset card's border stays visible in a system colour, and an inset card draws like a regular card, which is accepted because nesting carries no information. If the inset look must survive forced colours, say how. |
| SPEC-1-04 | blocking | spec.md FR-025, US4-3, US4-7 | A horizontal rail "wraps its items onto further rows" and puts "the bottom items at the inline end" with a block-direction divider between the groups. US4-7 has ten links but does not say which group they are in. The spec does not say where the bottom group and the divider go once the primary items wrap: on the first row, on the last row, or on a row of their own. A divider running in the block direction makes no sense across several rows. This is the narrow-width case #12's drawer will hit. | Define the wrapped layout with both groups present (which row the bottom group sits on, whether the bottom group wraps too, and the divider's direction and length once wrapped). Make US4-7 state the groups of its ten links and include bottom items. |
| SPEC-1-05 | blocking | spec.md US1-5, FR-013, FR-031 | US1-5 requires the eyebrow-variant heading's accessible name to be "the text as written, not upper-cased", while FR-031 draws it upper-cased. In Chromium, CSS `text-transform` text can show up in the accessibility tree in its transformed form. This was not probed here (no browser in the container). If Chromium exposes the transformed text, US1-5 cannot pass with a CSS uppercase. Any alternative that keeps the DOM text unchanged and draws it upper case is a design decision that should come before planning. | Before planning, probe Chromium's full accessibility tree for a slotted `h3` whose text is upper-cased by `::slotted` `text-transform`. If the name is the written text, record the probe and keep US1-5. If it is not, choose between accepting an upper-case name and another technique, and record the choice. |
| SPEC-1-06 | note | spec.md "Slotted headings", FR-012, FR-019; `base.css` lines 102-125 | `base.css` styles `h1` to `h6` inside `[data-ocelle-prose=""]` (margins, size, weight). The spec says the host page's rules win over the element's slotted styles. So a section header or page header placed inside a prose region draws its heading at the prose sizes and margins, not FR-012's or FR-019's. This is the library's own stylesheet, not a host's. | Add an edge case: a section header or page header inside a prose region. Either accept that and document it in the README, or exclude these slotted headings from the prose rules in `base.css` (a `@ocelle/styles` change the plan must then cover). |
| SPEC-1-07 | note | spec.md FR-010, FR-011, FR-019, US1-14, US2-5 | Once the actions wrap under the heading (or under the description), the spec does not give the block gap between them. FR-011 and FR-019 give only the inline `--ocelle-space-4` gap. It also does not say how the actions line up in the block direction on the page header (top, centre or first line), or when wrapping starts. | State the block gap in the wrapped state, and the actions' block alignment on the page header. |
