# Spec check 2

Inputs: `spec.md` as of `70431b8`, `checklists/requirements.md`, `reviews/spec/check-1.md` and `check-1-fixes.md`,
constitution 1.3.1, and, as they stand on the branch, `packages/tokens/src/source.ts` (token values, the `main`
ground list) and `packages/elements/README.md` ("Host ARIA", "Element conventions"). No browser probe was run.

Check 1's blocking findings: SPEC-1-01, SPEC-1-03, SPEC-1-04 and SPEC-1-05 are resolved as their fix notes say.
The rail numbers now agree: the 52 px rail with 4 px inline padding leaves a 44 px content box, a 40 px item centred
in it leaves 6 px a side in the border box, and the ring (3 px + 2 px offset) needs 5 px. SPEC-1-02 is resolved for
`size`, `variant`, `density` and `orientation`. But its new general rule in FR-006 breaks `inset` (SPEC-2-01).
Every token the spec names exists in `source.ts` except the four eyebrow tokens. `color-inset` and `color-rail` are
in the `main` ground list, so the eyebrow contrast entry (FR-030, FR-032) covers an inset card and the sidebar.

| SPEC-2-01 | blocking | spec.md FR-006, Key Entities "Variant attribute", FR-016, US1-10 | FR-006 covers `inset` as one of the variant attributes. It says "an absent, empty or invalid attribute value MUST behave as 'not set'". `inset` is a boolean, and in HTML a boolean attribute is written `<ocelle-card inset>`, whose value is the empty string. Lit's Boolean reflection also writes `inset=""`. Read as written, FR-006 makes the normal way to set `inset` do nothing, and a page that sets `card.inset = true` gets a reflected attribute that FR-006 then treats as not set. FR-016 and US1-10 assume presence means inset. | Limit the "empty or invalid is not set" rule to the enumerated attributes (`density`, `size`, `variant`, `orientation`). State that `inset` is a boolean: present (any value, the empty string included) means inset, and absent means not inset. Add `<ocelle-card inset>` (empty value) to US1-10. |
| SPEC-2-02 | blocking | spec.md FR-028, US3-12, US4-11, Edge Cases (unlabelled landmark); `packages/elements/README.md` "Host ARIA"; constitution III | FR-028 makes `label` win over a host `aria-label` and ignores a blank host `aria-label`. The library's documented convention says the opposite: "when present it decides alone: a blank host `aria-label` leaves the element unlabelled even with a `label`. When both are set, the host `aria-label` is the name". Under FR-028, a name set on the host does not reach the landmark when `label` is set. That contradicts constitution III ("an accessible name set on a host reaches the real inner control") even though FR-028 cites III. US3-12 ("Projects" wins over "Other") and US4-11 ("Me" wins over "Other") test the contradicting rule. | Follow the Host ARIA convention: a present host `aria-label` decides alone, a blank one leaves the landmark unnamed, and removing it falls back to `label`. Rewrite US3-12, US4-11, the edge case and the FR-036 README statement to match. If the operator wants `label` to win for landmarks, record that as a deviation from the convention and from constitution III's wording, and change the README convention with it. |
| SPEC-2-03 | blocking | spec.md FR-021, FR-022, US3-3, US3-11, US3-13 | "Each non-empty part has padding `--ocelle-space-4` on every side" does not say what a part is in the default slot. It could be the default slot's region as a whole (one padded block holding all sections) or each section (each assigned element padded, with a divider between padded sections). The two give different boxes, divider positions and baselines. The spec also does not say whether there is any gap between sections, or whether text in the default slot (US3-11) is padded. #497's complaint, and SC-006's "part-level padding and gap overrides", are about exactly this spacing, so the plan would be choosing the product. | State whether padding applies per section or per region. State where each divider lies relative to that padding, whether sections have a gap between them, and how US3-11's loose text is spaced. Add the padding to the outcomes of US3-3 so a test measures it. |
| SPEC-2-04 | note | spec.md FR-025, US4-2, US4-3, US4-7 | The spacing around the rail's divider is not given. Primary items sit at one end and bottom items at the other, with free space between them. The spec does not say where the divider lies in that space (against the bottom group, against the primary group, or in the middle), or what gap separates it from the groups. In the wrapped horizontal rail, the inline gap between the primary group, the divider and the bottom group is also unstated, and the per-row item count at 320 px depends on it. | State the divider's position (for example, `--ocelle-space-1` before the bottom group) and its gaps to both groups, in both orientations. |
| SPEC-2-05 | note | spec.md FR-025, US4 | A vertical rail "fills its container's block size", but the spec does not say what happens when its items are taller than the container (a short window): overflow, clipping or scrolling, and whether the bottom group still sits at the block end. FR-023 assigns scrolling to the container for the sidebar, but the rail has no such statement. | Add the overflowing vertical rail as an edge case with its outcome (for example: grows with its content like the sidebar, scrolling is the container's). |
| SPEC-2-06 | note | spec.md Edge Cases (card in a card), FR-017 | The spec states that an inner card's density is its own, but no scenario tests it. The case where this goes wrong is a regular card (density not set) nested in a compact card. Its header section header must draw regular, and a mechanism based on inheritance would make it compact. FR-017 also does not say what happens to a section header in a compact card's body, or wrapped in an element inside the `header` slot rather than assigned to it. | Add a scenario: a not-set card nested in a compact card has a regular-size header. State the size of a section header in a compact card's body or nested in its header slot (by FR-017's wording, regular). |
| SPEC-2-07 | note | spec.md FR-019, US2-2 | The page header's ground is not named (transparent, `--ocelle-color-canvas` or another token). US2 calls it "a band", but FR-019 gives padding and a rule and no background. | Name the band's ground, or state that it has none and shows its container's. |
| SPEC-2-08 | note | spec.md Edge Cases (heading slot holding no heading) | "A heading slot that holds no heading element (plain text or a `span`)": a text node cannot be assigned to a named slot such as `heading`; only an element with `slot="heading"` can. Plain text written in the host lands in the default slot, and neither header has one. | Drop "plain text" from the edge case, or state what a text child of a section header or page header does (it is not rendered, since there is no default slot). |
| SPEC-2-09 | note | spec.md SC-006, "Consumer need" | SC-006 lists five workarounds, among them "card density overrides". But the Consumer-need list of what kitty-mission-ui deletes names four (part-level padding and gap overrides, token-painted dividers, pinned page-header font rules, personal-rail `::part` overrides) and has no card override. The card bullet describes a missing density, not an override. | Name the card workaround in "Consumer need" (what Kitty Desktop does today for a dense card), so FR-036's README statement for the card has a source. |
