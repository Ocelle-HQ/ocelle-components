# Spec check 1

Read: `spec.md`, `checklists/requirements.md`, `triage/006-storybook-workbench.md`, constitution v1.3.1, and for the
facts the spec states, `gates/README.md`, `gates/gates.json`, `storybook/package.json`, `storybook/stories/*.ts`,
`storybook/.storybook/preview.ts`, `storybook/test/integration/setup.ts` and `.github/workflows/ci.yml`. No earlier
check exists. Confirmed facts: 12 stories (8 in `tokens.stories.ts`, 4 in `base.stories.ts`); fourteen required
checks today, so seventeen after; the theme global sets `data-theme` on `<html>`; the Storybook is built in CI only
through `pnpm -r build` in the `csp` and `prefix` jobs and in the run-time test's global setup.

| SPEC-1-01 | blocking | spec.md US1 AS2, FR-001, FR-017 (`storybook-build` plant "a story that does not compile") | AS2 asks the build gate to exit 1 on a story file with a **type** error. `storybook build` (Vite with esbuild) strips types and does not type-check, so a type-only error builds and the gate passes; the plant would fail the plant job, or the gate would have to type-check, which duplicates the `typecheck` gate whose scope already holds the repository TypeScript. The spec does not say which. | Either restrict AS2 and the plant to errors the build itself reports (a syntax error, an import that does not resolve) and state that type errors in stories are the `typecheck` gate's, or require the build gate to type-check the Storybook workspace and say why the duplication is wanted. |
| SPEC-1-02 | blocking | spec.md US1 AS3, FR-001, FR-017 (plant "a story module that throws") | "A story module that throws while the story index is built" describes no event the build produces: Storybook's indexer reads CSF files statically (it parses them, it does not execute them), so a module whose top level throws is indexed and built without error and only fails when it is loaded in a browser. As written the plant cannot be caught by a build gate, or the gate must load every module in a browser, which is the visual and axe gates' "fails to render" (FR-004, FR-014, Edge Cases). | Define the failure in terms the build exposes, for example "a story file the indexer cannot read (not valid CSF: a default export that is not a static object, a story export it cannot analyse)", and move "a module that throws when loaded" to the render-failure findings of `visual` and `axe` with a plant there. |
| SPEC-1-03 | blocking | spec.md US2 AS6, AS7, FR-008, FR-009, FR-018, FR-017 (`visual` breaking plant "no container") | The exit-2 conditions contradict the stated use. The baseline command is run by a contributor on the host "under podman or docker" (AS6, FR-008), yet FR-008 says it "MUST refuse (exit 2) to run outside the pinned container"; FR-009 joins "the container engine is not available" (a host-side condition) with "not running in the pinned container" (an in-container condition). The spec never says whether the gate and the command are host launchers that start the container, or in-container programs, or both layers. That decides what the breaking plant presents and how the plant job, which FR-018 runs in the pinned container, can show "no container" at all. | Name the two layers: a host entry point that needs a container engine and starts the pinned image by digest (exit 2 when no engine, or when the image digest does not match), and the capture inside it that refuses to run in any other image or browser build (exit 2). State which one CI's "Visual regression" job and the plant job call, and what the breaking plant changes to produce its cause. |
| SPEC-1-04 | blocking | spec.md FR-018, SC-003 | "Where the container is not available the plant job MUST report those plants as not run (exit 2 cause), never as passed" does not say what the Plants check itself then reports. If it passes, the `visual` plants are skipped silently, which is the vacuous gate Principle VIII forbids; if it exits 2, `pnpm run gate:plants` can never pass in a development environment without an engine (spec Assumptions: this sandbox), and every phase's local plant run fails. | State the plant job's exit when `visual` plants cannot run (for example exit 2 locally, and in CI the container is a precondition of the Plants job so that case cannot pass), and whether a local option runs the other plants with the skipped ones named. |
| SPEC-1-05 | blocking | spec.md FR-006, US2 AS6, SC-002 | Byte identity "under podman and under docker" and across runs is required, but no requirement says where it is proven or how often. No gate, CI job or test is named that captures twice and under both engines and compares; SC-002's "100% of cases" has no defined set of cases. As written it is a property that is asserted once and never shown false by a test that could fail (Principle VIII). | Add a requirement for the check that proves it: for example a CI job (or a step of the "Visual regression" job) that produces the baselines under docker and under podman, twice, and fails on any byte difference, with a plant (a capture input left unfixed, such as an animation without reduced motion, or PNG metadata with a timestamp) that makes it fail. Name the set SC-002 measures (every story-theme of the built index). |
| SPEC-1-06 | operator | spec.md US2 ("on any machine"), FR-006, FR-007, SC-002 | "Any machine" is not defined. Chromium's rasterisation differs between CPU architectures, and a multi-platform image digest resolves to a different image on an arm64 host (for example a contributor on Apple Silicon with podman), so byte identity across machines holds only if every capture runs the same platform image, which on arm64 means emulating linux/amd64 (slow) or giving up identity there. Which hosts must produce CI's bytes is a product decision. | Operator question below; the spec then states the platform (for example "the linux/amd64 image, by its manifest digest, emulated on other architectures") or the supported hosts. |
| SPEC-1-07 | blocking | spec.md Edge Cases (Fonts; Theme leakage) | Two edge cases are written as requirements ("must not fall back silently", "a story that requests a font the container cannot serve fails the run"; "must not leave the previous theme's state", "the dark capture equals the capture rendered fresh in dark") but have no FR, no acceptance scenario and no plant, so planning may drop them. A silent font fallback would bake the wrong typeface into committed baselines that then pass forever. The fonts case also leaves open which fonts other than Schibsted Grotesk may appear in a capture ("fonts inside the pinned container"), against constitution II's single type family. | Add FRs: the `visual` gate (and the baseline command) fail a story whose rendered text uses a font face that is not loaded or not on an allow-list (Schibsted Grotesk; name any other), with a fail plant; and each theme's capture is made in a fresh page or is shown equal to one, with a test that would fail on leakage. |
| SPEC-1-08 | blocking | spec.md FR-013, US3 AS2, SC-003 | "One finding per violation ... and a selector of the node" is ambiguous when one axe violation lists several nodes (the usual case for `color-contrast`): one finding with one selector, one with all, or one per node. SC-003 and the plant job require "exactly its expected findings", so the count must be fixed. | State "one finding per violating node (story id, theme, rule id, impact, the node's selector)" or "one per rule per story-theme listing every node", and write the plant expectations to match. |
