# Implementation plan for selectable workflow steps

**Branch** `027-workflow-node` · **Date** 2026-11-23 · [Specification](spec.md) · [Approved triage](../../triage/027-workflow-node.md)

## Summary

Add an `ocelle-workflow-node` element with one native selection button. The host supplies step content, the stable node ID, selected state and run or validation status. The node requests selection and displays the state it receives. The same action supports standalone use and host-managed focus in the canvas. [Public contract](contracts/workflow-node.md)

## Technical context

Use the repository’s pinned TypeScript, Lit and Chromium without new dependencies. Keep host data in the element’s public inputs. Use Vitest for element and gate tests and the built Chromium harness for keyboard, accessibility and strict CSP. Storybook supplies the visual fixtures and pinned light and dark baselines.

## Constitution check

Use the existing registration, token, button, focus and visual conventions. Keep built-in accessible references inside the shadow root. Resolve host references in the host’s own tree and associate the resolved elements with the button. From the first public phase, the button itself meets `--ocelle-target-min` in both dimensions, shows the token focus ring, and uses checked foreground and ground pairs for its control and state cues. The card rule is decorative. Supply light and dark stories and pinned baselines for the variants and states each phase exposes. Ship one new standalone entry and one `ocelle-` event as a MINOR addition. The element makes no network calls and has no graph editing or workflow execution. Each behavior slice starts with named failing assertions, passes focused replay and changed-source mutation, and retains the full required CI gates.

## Project structure

- `packages/elements/src/ocelle-workflow-node.ts` holds the element and its native control. Register and export it through the normal standalone entry, browser build and complete exports.
- `packages/elements/test/workflow-node.test.ts` runs in the in-process `elements` project, which Stryker includes for changed element source. Give every phase’s changed public behavior a failing assertion there. `packages/elements/test/browser/workflow-node.test.ts` repeats relevant consumer paths against built output in the separate strict-CSP `elements-browser` project. Share a scenario when the same assertions run in both harnesses. Keep the in-process assertions even when the built fixture covers the same path.
- `storybook/stories/workflow-node.stories.ts` holds the fixtures. Add their committed light and dark baselines and update the manifest, README, changelog and related exact inventory tests.

## Delivery sequence

1. **Select and identify a step.** Record a separate test-free inert scaffold. Wire the module, standalone package entry, aggregate exports and browser registration used by the selected runners, and keep the existing exact inventories compatible before the red commit. Then add test fixtures, scenarios and assertions in the test-only commit. First assert that the native selection action exists through a null-safe DOM observation so the absent action on the scaffold fails a named assertion before a driver requires it. Prove the two example steps, native activation and event dispatch, stable IDs after renaming, unchanged host data, and accessible host information reaching the button. Implement the standalone action with its token focus, target floor, and contrast affordance. Verify the keyed replacement gesture and one standalone Tab stop. Approve the slice with its own light and dark stories and baselines, including its focused presentation.
2. **Navigate and read combined states.** In `elements`, prove the newly host-controlled removal and restoration of sequential participation, direct focus and activation while excluded, and the newly combined accessible and visible states. Keep the already-working standalone tab stop and ordinary selection as regression assertions. Verify the full title and metadata at narrow width, preserve built-in state text when host context is updated or removed, and repeat the relevant paths in built Chromium. Add light and dark baselines for newly introduced states and check the token affordance and visible focus under forced colors.
3. **Inspect a recorded run.** Make the newly readable host status the phase red in `elements`. Exercise existing selection and unchanged host data in the same inspection fixture as regression assertions. Add the noninteractive status slot and inspection fixture with light and dark baselines. Repeat the relevant inspection path with the built package under strict CSP. Verify docs and exact inventory with the same selection contract in both modes.
