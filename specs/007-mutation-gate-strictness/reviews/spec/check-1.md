| SPEC-1-01 | blocking | spec.md FR-003, FR-004, US1 AS6, Key Entities "Zero-mutant file" | The zero-mutant unit is inconsistent. FR-003, FR-004 and the Key Entity define it per **file**; US1 AS6 speaks of "zero-mutant **entries**" in a `--files` shard run. In CI every run is a shard run, and one file of more than 60 changed lines is split into entries that never share a shard (001 FR-013; `gates/lib/mutation/shards.ts`). So for `source.ts:61-120` with no mutant on its changed lines while `source.ts:1-60` has mutants, the spec gives two answers: the shard of `61-120` names the file as zero-mutant (entry reading), or names nothing because the file has mutants in another shard (file reading, which a shard cannot see). The summary count ("zero-mutant files") inherits the same doubt. | Say what a shard run reports and counts: either a zero-mutant entry (`path` or `path:start-end`, the entry as given to `--files`) or a file, and how the line is worded when the unit is a range. Make FR-003, FR-004, AS6 and the Key Entity use the same term. |
| SPEC-1-02 | blocking | spec.md US2 Independent Test, AS1, AS2; FR-009; FR-010; SC-003; SC-004 | The run that FR-009 and FR-010 judge is not defined, and the results depend on it. The Independent Test says "run the mutation tool on the whole of `source.ts` in the entries the gate's plan makes for a change of every line"; AS1 and FR-009 say "in the gate's 60-line entries". Op 004's figures, which the spec uses as the baseline (121 Timeouts, 578 s), came from raw Stryker with a scratch config with the TypeScript checker **off** (`ops/004-token-source-mutation/mutation/README.md` § How the whole-file runs were made), while the gate and the CI shard run with the checker **on** (lines 25, 27 and 30 then end as CompileError, op 004 L1-03), which changes both the statuses and the wall time. "Wall time" (AS2) is also not tied to a command: Stryker alone, or `gate:mutation --files <entry>` including its git and record scan. A plan could meet 176 s under one reading and miss it under the other, and the red run (op 004's reports) and the green run would not be comparable. | State the command and configuration of the sandbox runs: for example `gate:mutation --base <a base that makes every line of source.ts changed> --files <entry>` with `stryker.config.json` as committed (checker on), wall time of that command; and say that the op 004 runs are the red evidence only with their recorded difference (checker off), or that the red run is repeated under the same configuration. |
| SPEC-1-03 | blocking | spec.md US2 AS3, FR-010, SC-004, Assumptions "480 s" | "Finishes within 480 s as a `mutation-shard` job" has two readings that give different verdicts. The Assumption says 480 s "leaves 2 minutes of the 10-minute job limit for setup and runner variance", which reads as the time of the gate step only; AS3 and FR-010 say the **job** finishes within 480 s, which includes checkout and `./.github/actions/setup`. A job of 520 s with a 420 s gate step passes one reading and fails the other. | Name the measured quantity: the `mutation-shard` job's duration as GitHub reports it, or the duration of its `gate:mutation` step; and keep the Assumption's reason consistent with that choice. |
| SPEC-1-04 | operator | spec.md US2 AS3, FR-010, Assumptions "CI measurement" | The CI half of FR-010 may have no run to measure. CI runs only on `pull_request` (`.github/workflows/ci.yml` `on:`), and `mutation-plan` makes shards only from the pull request's changed lines. The mission's own pull request has a `source.ts:121-180` shard only if its diff changes those lines; FR-012 forbids changing the built outputs, and the lever may be configuration or test order alone, so the mission's diff may not touch `source.ts` at all. The spec leaves the choice to the plan ("the mission's pull request (at landing), or on a run the operator starts"), but both options need something only the operator can allow: a measurement commit on the pull request that changes every line of `source.ts` without changing outputs (and is reverted before merge), a separate branch or pull request pushed for the run, or a manual trigger added to `ci.yml` (a CI change not named in scope). | Operator: choose how the CI run of FR-010 is produced, and record it in the spec's Assumptions. |
| SPEC-1-05 | operator | spec.md US2, FR-010, SC-004; 001 FR-013 | The spec bounds each `source.ts` entry measured **alone**, but 001 FR-013 lets an entry share a shard with entries of other files up to 10 entries and 250 changed lines. A pull request that changes `source.ts:121-180` and, say, 190 lines of `generate.ts` or gate source puts them in one shard, whose time is the sum. Neither the requirements nor *Dropped* covers this case, so under the no-follow-ups rule it is neither done nor listed as dropped. | Operator: decide whether a shard holding a `source.ts` entry together with other files' entries is in scope (then FR-010 needs a bound or measurement for it, possibly through FR-014) or is dropped (then add it to *Dropped*). |
