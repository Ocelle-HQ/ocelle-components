| PLAN-FRESH-2-001 | confirmed | fork | a | research.md § R-06 criterion 3 asks that "the `statusReason` message or the killing test's name names the mutated record". Two things make that undecidable as written. First, `vitest-helpers.js:37` passes on only `errors[0].message`. Second, the killers (`source-table.test.ts:39-43`, `:45-52`, `:77-93`) compare one object keyed by every token. My probe of Vitest 5.0.5 reproduced the message `expected { 'space-0': '0.25rem', …(119) } to deeply equal { 'space-0': '0.25rem', …(119) }`, which names the first key and not the mutated one. The test names name a field word and no record. Read strictly, the criterion fails for every Killed former Timeout and wrongly triggers levers 2 and 3. Read loosely, it passes for every mutant. Either way it does not test spec FR-011 / US2 scenario 4. Options: (a) the lens remedy. Criterion 3 becomes "`killedBy` is one of a named list of per-record value/group tests (source-table.test.ts's light, dark and JSON tests)". The record is tied to the kill by the by-hand application (the Vitest diff names the key). `statusReason` is recorded as given, not judged. A failure due only to message text never triggers lever 2 or 3. (b) Make the per-mutant tie decidable in the tests themselves: split the light, dark and JSON comparisons of `source-table.test.ts` into one assertion per record (for example `it.each` over `expectedTokens`, or `expect(..., name)` messages), so that `killedBy` / `statusReason` name the record for every kill. This costs a test change in `packages/tokens/test/` and more test cases in the token project's first group. |
| PLAN-FRESH-2-002 | confirmed | fork | a | `concurrency-token-provider.js:19-30`: with the checker there are `ceil(c/2)` checkers and `floor(c/2)` runners (4 + 4 at 8). With the checker off, group A's expected CompileErrors (spec FR-011, R-05) run the whole suite instead. So the two runs in research.md § R-06 "The checker split" differ in runner count, mutant set and overlap. Their difference is not the checker's share, yet R-05 § Lever 2/3 and plan.md § Summary use it to skip lever 2 and go to an FR-014 amendment of 001 FR-013. Options: (a) drop the "checker share alone > 176 s → straight to lever 3" shortcut. Decide the levers on the measured entry time only (FR-010), always trying lever 2 before lever 3, and keep the split as a labelled diagnostic. (b) Measure a defined bound: run without the checker at `concurrency` equal to the checker run's test-runner count (4), record the checker run's CompileError count beside it, state the share as a bound with its direction, and let only a bound that holds in the right direction skip lever 2. |
