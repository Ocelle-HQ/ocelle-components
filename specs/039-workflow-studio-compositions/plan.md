# Implementation Plan: Workflow Studio Compositions

**Branch**: `039-workflow-studio-compositions` | **Date**: 2026-11-28 | **Spec**: [spec.md](spec.md)

## Summary

Deliver three independent, executable Storybook compositions in the issue’s order. Each uses an external fixture host with resettable fictional state. The existing package controls own rendering and native interaction. The example hosts handle graph and layout state, simulated decisions, and fixture-specific focus transitions. Keep the product-facing package surface unchanged. The approved semver impact is none. [Triage](../../triage/039-workflow-studio-compositions.md)

## Technical Context

- **Language and dependencies.** Repository-pinned TypeScript, Node, pnpm and Storybook. Use the existing generated custom element types, DOM and native form behavior. Each fixture host has no component runtime imports.
- **State.** Deterministic per-mount values. Authoring stores ordered semantic graph, layout, viewport, selection and inspection state separately. The interview fixture keeps pending form data and accepted timeline events. The catalog fixture stores separate accepted bindings and pins by instance identity. All state is in memory.
- **Runtime and tests.** Use the existing in-process `storybook-browser` project for actual host interactions and Mutation. Use built Storybook under its normal harness and the packaged elements under the strict same-origin fixture server. Test light, dark, forced colours, real keyboard and tap, a regular and a narrow layout, and reachable focus.
- **Scope and performance.** One new built example and two pinned baseline PNGs per phase. Run focused replay and scoped Mutation before review. Keep the required Visual, Axe, strict CSP, Plants and full landing CI. Use the measured inventory and runtime on each exact pin.

## Phase 1 — Author the branching workflow

Mount one ordered graph with distinct destinations and an unrelated surviving connection. The button-mode action-row palette adds one Security review immediately before the visible Publish decision successor. The list-detail presents the graph and inspector, with a visible status indicator and finding action for a missing binding. Give the enabled reviewer form-select a real Unassigned option with an empty value. Set the field's public `value` from the selected step's authoritative binding when it mounts, changes selected step or switches inspector route. Verify the initial Unassigned choice agrees with the missing-binding finding. A trusted choice of the named reviewer changes that step's binding and clears the finding. A width or route change retains the accepted choice.

Observe the recipe's list-detail border-box inline size and use the published one-column collapse threshold resolved at the fixture's root font size. Keep the observed compact route and public `narrow` input in sync. Set public `detailOpen` for the active list or detail pane in one column. Use the inline inspector outside the compact route and the real drawer in the compact route. The finding preserves selection and focuses the visible enabled reviewer through public `focus()` after the chosen route settles. In the built check, hold the viewport wide and narrow the recipe container below the collapse threshold. Deliver the finding action, observe the real open drawer and deep focus on the reviewer, and verify that selection and binding survive the route change. Also cover the ordinary narrow viewport.

Use the existing canvas controls for real keyboard and tap selection, numeric movement and named destination edits. Record the delivered composed request before the host decides. Capture independent immutable serialized values from a read-only observation of the fixture's authoritative semantic store, including the named reviewer and connections. Movement changes the visible position with identical semantic bytes. Rewiring changes only the intended source and outcome connection. Rejection keeps the previously accepted edge and semantic bytes and exposes the attempted destination in the notice. Enable the notice's existing polite `announce` behavior for this rejection. Verify one meaningful live feedback update and focus retained on the operable editing control. After switching the same graph to read-only, prove gestures reach their rendered targets, selection and viewport navigation work, and the observed stream holds zero edit requests.

Expose one discoverable author-only Remove Security review action for the selected step. Operate it by keyboard and tap. Apply a single host update that removes the selected step, its binding, all incoming and outgoing connections and its layout entry. Reconcile selection and inspector state to the surviving step or clear them when no step is selected. Preserve unrelated records. From the visible action prove exactly one removal, absence of every deleted reference in authoritative snapshots, a surviving unrelated edge, and deep focus on the operable Publish decision selection action. For host-owned focus loss, use a host-owned selection action for the visible successor or previous survivor. When only clipped steps remain, keep an operable, visible Step selector available for selection or reveal. Keep a persistent Add step control for an empty graph. Use the native Step chooser for reveal targets and the real selection path to set host selection. Check the previous, Step and Add step fallbacks and keep unaffected focus. Preserve the canvas's own keyed recovery when its focused action is removed.

## Phase 2 — Inspect the run and answer the planning interview

Use the same component contracts with a new immutable fictional graph, read-only mode, and independent selection and viewport. Present the recorded status and decision facts. Observe real selection and viewport requests and show target reachability before the zero-edit assertion.

Open a real named dialog. Mount a native form with the existing form textarea. Read the submitted value through FormData. Reject the first save with the control's accessible error, keeping the textarea identity and value. The first fixture exercise keeps “one hour”. A separate reset fixture exercises the two-line content and preserves the newline, subsequent edits and retry. On accepted retry, append one answer event. The event timeline presents the data owner and engineering lead, distinct actions and evidence, and the stable named plan revision. After the public dismissal event and the rendered pane update, return focus to the real operable opener or the visible Step selector when the opener is unavailable. Narrow state transitions keep pending text, selection and visible evidence.

## Phase 3 — Compare and accept a catalog upgrade

Use the existing version and capability comparison recipe with fictional admitted offers. Keep distinct instance records and reviewer bindings. Open the comparison with a stable instance identity and render separate current and offered versions, digests and capability changes. Preview and dismiss leave both pins intact. On an explicit accepted save, update only that instance and preserve both reviewer bindings. On dismissal after the public lifecycle settles, use the operable visible comparison opener or the relevant visible instance selection action in the compact layout.
