| SPEC-1-01 | blocking | spec.md header "Code-block content model (clarify 3)"; FR-020; FR-035; Edge Cases "Markup inside a code block" | The content model contradicts itself. The operator's answer is "slotted text", which is triage option (a): "slotted text into a shadow `<pre>`", meaning a `<slot>` inside the shadow `pre`. FR-020 and the edge case say that child elements "add no markup or style" and that a `<b>` adds no style. That only holds if the shadow root shows a copy of `textContent` and does not slot the light DOM, because a slotted `<b>` keeps its bold styling. Digest mode (FR-029, FR-030) also has to render a split copy, since slotted text cannot be split into groups. FR-035 still lists "its default slot (the text)". The manifest must list only slots that exist (constitution I). A plan could pick either model, or slot in one mode and copy in another, and every choice breaks one of these statements. | State one model. Either (a) the shadow root renders the trimmed or verbatim `textContent` and has no default slot, so FR-035 lists no slot and says the text is read from light DOM, or (b) a real slot, with digest mode rendering a copy and the "adds no style" statement dropped. If (a) departs from the operator's "slotted text" answer, record the operator's confirmation. Also state what the overflow-region module's `slotchange` trigger and focus-handover walk see under the chosen model. |
| SPEC-1-02 | blocking | spec.md US1 scenario 7 | The scenario does not give the state before the task, and its assertion is "at most one" event. If the disclosure starts closed, true-then-false gives zero events, and "at most one" also passes with zero. If it starts open, setting true changes nothing and false gives one event. Both readings pass a test that sees zero events, so the coalescing (FR-012) has no assertion that could fail (Principle VIII). | Split it into two scenarios with a stated start state and an exact count. Closed, then true and false in one task: exactly 0 events. Open, then false and true in one task: exactly 0. Closed, then true, false and true: exactly 1, with `detail.open === true`. Wait a stated time (for example the next task plus `updateComplete`) before counting. |
| SPEC-1-03 | blocking | spec.md US2 scenario 12 vs FR-033 | The two disagree on where a digest may break. FR-033 lets a digest break "only between groups or between the prefix and the first group". Scenario 12 forbids a break between the prefix and the first group "unless the prefix alone fills the line". Also, "the prefix alone fills the line" cannot be measured as written. | Pick one rule and write it the same way in both places. For example, a break is allowed between the prefix and the first group and between groups, and never inside the prefix or a group. Make scenario 12's assertion the set of allowed break positions, measured from line boxes (for example the `getClientRects` of each group). |
| SPEC-1-04 | blocking | spec.md US2 scenario 11; FR-032; SC-004 | "Read as one string, not as 16 separate words or nodes" names no observable. Chromium's full accessibility tree has one StaticText node per text node, so 17 adjacent spans give 17 nodes whatever a screen reader says. Read that way, the test always fails and forces FR-032's fallback. Read as concatenated text, it always passes. SC-004's "its Chromium accessibility text is the same string" has the same gap. | Name the measure: which tree or API (for example CDP `Accessibility.getFullAXTree`, or Playwright's `ariaSnapshot`), which node, and which property (name, or concatenated StaticText in tree order), and what counts as "separate words". The plan then measures that quantity and FR-032's fallback applies only when it fails. |

| SPEC-1-06 | note | spec.md FR-012 ("coalesced as native `details` coalesces its `toggle`") | Calling the rule native is inaccurate. The spec's own explicit rule (no event when the final state equals the state before) is stricter. FR-012 also does not say how a script-set change is batched into "one task", given that Lit updates in a microtask. | Drop "as native `details` coalesces", keep the explicit rule as the definition, and state when the event is dispatched relative to the change (for example in a task after the change, after the host attribute is reflected). |
