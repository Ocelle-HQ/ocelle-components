# Tasks: Feedback and Forms

**Input**: design documents in `specs/010-feedback-forms/`, as approved at the plan gate on 2026-11-13 after three
plan-squad rounds (`reviews/plan/round-1..3/`):
- spec.md (FR-001 to FR-036, SC-001 to SC-007, the operator decisions at the top);
- plan.md, decisions 1 to 11 and the phase list;
- research.md, R-01 to R-11;
- data-model.md (the notice and form-control state, both transition tables, the alert path);
- contracts/elements.md and contracts/testing.md (capture, driver steps, twins table, plants table);
- quickstart.md.

**Tests**: required. Constitution Principle VIII applies to every phase. The phase flow, as the story extension's
scripts support it (`.specify/extensions/story/scripts/`; analysis C1, C2):
- **Phases 2 to 4**: `base.sh`, then one scaffold commit recorded by `scaffold.sh` (T009a, T029a, T049a: the phase's
  new `src/` modules with their signatures and no behaviour, no test file, nothing wired into existing code), then one
  red commit of test files only proven by `red.sh`, then green, `tdd-check.sh` (checks 1 to 4, check 3 against the
  scaffold) and an independent review. Each scaffold task names what the red tests fail on against it.
- **Phase 1**: no scaffold is possible. Its new code (`test/live-reading.ts`, `test/live.ts`, the driver files,
  `test/in-process.ts`, `test/browser/serve.ts`) matches the test pathspec (`story-config.yml`: `**/test/**`), which
  `scaffold.sh` refuses, and `tdd-check.sh` check 2 overlays it, as a changed test-path file, onto the base. So the red
  commit carries signature-only stubs of those modules (T001d), and T005a records the evidence check 2 cannot give:
  the final test files run against the red commit's stubs, kept with the review.
- **Phase 5**: no scaffold (the stories are test paths too). `main` is merged before `base.sh 5` (T060), and T061's
  red test also asserts each new story's committed baselines (not a test path), so check 2 fails on the missing
  baselines for the right reason; T066 records how the check reads.

Every test change of a phase, the README documentation test's assertions and the pinned element lists and counts
included, is in that phase's red commit (analysis I3, U2, I7); green may complete test infrastructure (the capture,
the driver, `test/in-process.ts`) but adds no assertion. Records that are not test files
(`packages/tokens/contrast/pairs.json`, `source.ts`, README text, manifest and the manifest plants' copies, CHANGELOG,
`package.json` exports) change only in green (analysis I1); a scaffold adds only new `src/` modules. Expected values are written by hand from the spec and the contracts, never read from the source under test:
announcement counts from the spec's scenarios and the SC-002 matrix, form outcomes from `contracts/testing.md`
§ Twins, colours from the token names the spec names, timing from the literals 150, 350 and 5000 ms.

The guard rules:
- Every announcement assertion states its count once and checks it under both `"settled"` and `"rendered"`
  (`expectAnnouncements`, no condition). A zero count never stands alone: its scenario also asserts the positive
  outcome it guards (the region present, the text visible, the host role).
- Every native-twin comparison also asserts the absolute outcome of the twins table.
- Each plant of `contracts/testing.md` § Plants is a row of `test/plants.test.ts` and is run by the implementer; the
  output goes to `reviews/phase-<n>/plants.md`. A plant that does not make its guard fail stops the phase.

**Shared scenario bodies** (005 R-11): every browser scenario is written once in
`packages/elements/test/scenarios/*.ts` against the driver and run by the in-process `elements` project (element
source, mutated, test timing of decision 11) and the `elements-browser` project (built browser build on strict-CSP
fixture pages, real timing). Fixture runs also assert zero CSP violations, only allowed requests and no console
message.

**Environment**: Node 22 in this container, 26.13.0 in CI. Browser runs set `OCELLE_CHROMIUM_PATH` as
`knowledge/speckit-flows/findings/frontend-missions.md` § Browser path says; one heavy job at a time; never
`git stash`.

**Organization**: Phase 1 is Setup (the capture and driver carry behaviour and go red first). Phases 2 to 4 are User
Stories 1 to 3, one review unit each. Phase 5 is User Story 4 and **starts only after #10 (mission 006) is on `main`
and the R-08 recheck (T060) is done**. Records (README, CHANGELOG, manifest, entry points) belong to the phase whose
behaviour they describe; there is no polish phase. Each phase is folded after its approval.

**Implementation waits for #10** (operator wave planning): no phase starts before #10 is merged.

- **Any mutation shard over CI's job limit**: 10 minutes, or 75 minutes for a shard holding `packages/elements/src/`

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an incomplete task)
- **[Story]**: the user story (US1 to US4)
- **`[-]`**: a task moved out of this mission by the operator's decision, not done here (T041a and T041b, moved to
  op 017, #42), or withdrawn by a later operator round (T025e, withdrawn by operator round 7; T025f to T025j,
  withdrawn by operator round 8, each with a note saying what of it was done and what is undone); its text is kept
  as it stood. The story scripts count only `[ ]` and `[X]` lines, so a moved or withdrawn task is neither
  open nor done.
