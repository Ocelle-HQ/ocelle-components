| SPEC-1-01 | blocking | spec.md "What 'announced' means here"; US1 scenarios 8, 9; SC-002 | An announcement is defined as a change in the text of a live region node that "existed in the tree before the change". When a notice is inserted (scenarios 8 and 9, which are the main case the operator decided), the region cannot exist before the change, because the insertion is the change. Read literally, scenarios 8 and 9 cannot pass, or a test has to make up its own pass condition. | Define the insertion case: after insertion the region is in the tree with empty text, then in a later accessibility-tree update its text becomes exactly the announced text, and this happens once. Apply the same rule when `announce` is set and then a change follows (scenario 14). |
| SPEC-1-02 | blocking | spec.md FR-008, FR-009; US1 scenarios 7, 15 | `role="alert"` and `role="status"` on the host make the host a live region by themselves, whether or not `announce` is set. The spec does not say what happens with `role="alert"` or `"status"` and no `announce`. Scenario 7 and FR-008 say "no live region node exists… nothing is announced", which the host's own role contradicts. With `announce` too, the inner live region sits inside the host's live region, so "never by two live regions" cannot be measured as written. It is also unspecified whether a server-rendered `role="alert"` notice announces on first load. | State the outcome for each pair of {no role, `alert`, `status`, other} and {`announce`, no `announce`}. Include first load and the case of nested regions. Say how "one change, one live region" is measured in the accessibility tree, for example as the number of live-region ancestors whose text changed. |
| SPEC-1-03 | blocking | spec.md FR-008; US1 scenarios 11, 13; Key Entities "Notice" | The notice's "text" (heading and body) is not defined. It could be the `textContent` of the slotted nodes, or the accessible text (including an `ocelle-icon` `label`, `alt`, and leaving out `hidden` or `aria-hidden` descendants). It is also unclear whether a change to text inside a slotted element counts (a `characterData` change in a slotted `<a>`, or an attribute change that alters an accessible name). The tests require the region text to be "exactly the announced text", so the source of that text has to be fixed. | Define the announced text precisely: which nodes count, whether accessible names of slotted elements count, whether hidden descendants count, and which mutations count as a "change". Add one scenario with a slotted link and icon. |
| SPEC-1-04 | blocking | spec.md US1 scenario 4; FR-006 | Text nodes cannot be assigned to a named slot. Only elements with `slot="heading"` can, so "only whitespace text there" cannot happen. FR-006 shows the heading box whenever an element is assigned. That means `<span slot="heading"></span>` or `<span slot="heading"> </span>`, which is what a server template writes for a null heading, still draws the heading box and the gap. That is the #513 defect this feature is meant to fix. | Decide and state whether the heading counts as absent when the text content of its assigned elements is empty or whitespace (recommended, for server-rendered hosts). Correct scenario 4's wording to match, and add the empty-`<span>` case. |
| SPEC-1-05 | blocking | spec.md SC-004 vs US1 scenario 4 | Scenario 4 measures from the box's top border edge to the first line box and expects that distance to equal the block-start padding. SC-004 expects "zero pixels between its top padding edge and its body's first line box". In CSS the padding edge is the outer edge of the padding, so SC-004's distance equals the padding and is never zero. Scenario 4 also ignores any border width, and FR-010 adds a 1 px border in forced colours. The two checks disagree, and SC-004 is false as written. | Use one measurement in both places: the distance from the content-box top to the top of the first line box of the body is 0, in both sizes, with and without forced colours. |
| SPEC-1-06 | blocking | spec.md FR-028 ("2 px wide"); FR-010, FR-025 ("1 px") | Constitution II forbids raw size literals in element CSS. "1 px" corresponds to the existing `--ocelle-border-width`, but the spec does not name it. No token exists for a 2 px boundary (`border-width` 1px, `focus-width` 3px, `bar-width` 3px). Planning on FR-028 as written gives either a lint failure or an unplanned token. | Name the tokens: `--ocelle-border-width` for 1 px, and for the error boundary either an existing token (for example `--ocelle-bar-width`) or a new token declared as part of this feature's surface (MINOR, changelog). |
| SPEC-1-07 | blocking | spec.md US2 scenario 16; FR-020 ("history restore or autofill"); US3 scenario 7 | Browser autofill cannot be triggered from a script or test in Chromium. As far as this check can see, Chromium also does not call the form-state restore with the `autocomplete` reason for form-associated custom elements. Autofill therefore cannot be shown true or false by a test that could fail (Principle VIII). History restore can be tested. | Keep history restore, measured by navigating away and back. Either drop autofill or move it to the README's "not measured" limitations, as WebKit is. |
| SPEC-1-08 | blocking | spec.md FR-022; US2 scenario 13; Edge Cases ("Both `label` and an external `<label for>`") | The spec lists three name sources (`label`, an external `<label>`, host `aria-label`) but gives no precedence when `aria-label` is combined with either of the others. In native accessible-name computation, `aria-label` overrides labels. Host `aria-labelledby` is not covered (an ID reference into the document). "With no duplicate words from the same source" is vague and not testable. | State the exact name for each combination, for example: `aria-label` wins; otherwise the external label(s), then `label`, joined by one space. State that host `aria-labelledby` is not supported, as `aria-describedby` is not, and replace the duplicate-words clause with an exact expected string. |
