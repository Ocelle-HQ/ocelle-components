# Research — Anchored popover for compact controls

## Native interaction and overlay order

Use `popover="manual"` with a shadow-local native `type="button"` and declarative `popovertarget`. The panel is the next element in its invoker’s focus scope and contains slotted native controls. Native activation handles Enter and Space and follows the platform pointer-focus behavior. The element supplies focused Escape and light dismissal. The alternative `auto` popover loses the underlying surface when a separately mounted foreground modal calls `showModal()`, and may leave focus on a projected control as it hides.

A Chromium 156 mechanism probe verified Tab and Shift+Tab through projected controls, excluding the disabled control. A nested modal and an externally mounted modal both handled the first Escape and returned focus to their opener while a manual popover stayed open. Explicit Escape for the second press closed the popover and focused the trigger. Use the same placement-independent cases on the actual component. Keep `autofocus` off surface content so opening does not transfer focus.

The round-one probe reached a native external Tab stop whose hit point was still covered by the open manual panel. Keep native sequential navigation and close the panel only after that navigation exits its scope, leaving the new focus undisturbed. The same probe reproduced native Escape clearing of a populated search field. Defer that first Escape as the existing overlay does. [Plan review](reviews/plan/round-1/refute.md) · [Overlay Escape policy](../../packages/elements/src/overlay.ts)

The native invoker and manual Popover API are available from Chromium 114 and Safari 17. Constructed stylesheets are available from Chromium 73 and Safari 16.4. Avoid `showPopover({source})` and CSS anchor positioning because the WebKit floor lacks them. The mechanism probe used Chromium 156. The WebKit 17 branch stores the invoker before it branches on popover mode. Its focus navigator enters an open invoker’s popover scope in either mode. Compatibility evidence must identify the browser version that actually ran. ## Placement and strict CSP

Borrow the tooltip’s fixed top-layer box and adopted stylesheet with a rule owned by each instance. Measure the trigger in CSS pixels, the owner document’s layout viewport, and the visible viewport using valid VisualViewport offsets when available. Size the panel to the available region before clamping it. Schedule the first frame during opening beforetoggle, verify the native open state before measuring and keep an unpositioned panel out of view. Follow anchor movement while open on one animation frame loop, cache geometry to avoid redundant writes, and release the loop and listeners on close or detach. Observing only resize misses a same-size anchor that moves in its layout or through a transform.

A Chromium 156 strict-CSP mechanism probe used external script and constructed sheets in a transformed clipping ancestor. Trusted Tab reached projected controls including a final control that required internal scrolling. The panel escaped clipping with no CSP violations and without expanding the viewport. Keep separate actual-component tests at 320 CSS pixels and at 200% text. [Existing tooltip placement](../../packages/elements/src/ocelle-tooltip.ts) · [Strict-CSP overlay test precedent](../../packages/elements/test/browser/tooltip.test.ts)

The review probe also confirmed that responsive removal of a trigger’s rendered box can leave a connected manual panel logically open. Close when the open lifetime loses that box, clear its pending work and require fresh activation after visibility returns. Use the priority and minimum visible extent in the [element contract](contracts/element.md) instead of flipping a scrollable preferred placement to a larger opposite side.
