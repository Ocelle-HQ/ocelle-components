(b) Add a `ResizeObserver` on each assigned element whose callback only schedules a pass for the next frame. | PLAN-FRESH-3-002 | confirmed | fix | - | Reproduced, with one correction to the lens's evidence. Stand-in: a flex-row host 1196 px wide, a shadow grid (288 px, `minmax(0,1fr)`, 304 px), a sizer set through an adopted constructed sheet, and a host `ResizeObserver`. A slotted element's own `ResizeObserver` appends a wider row when the element is resized. **One column, detail shown** (sizer 1072 px above the shown content): with the pass in the `MutationObserver` callback, the host went to 1192 px and `window` got "ResizeObserver loop completed with undelivered notifications."; with no pass, no error and 1072 px; with the pass scheduled in `requestAnimationFrame`, no error and 1192 px. So R-13's "nothing writes the sizer from inside a `ResizeObserver` delivery" is false for mutations made inside a delivery, and only a task-made mutation is tested. **Correction:** in three columns (the lens's p3 setting), the same error appeared with no pass at all and with the rAF-scheduled pass. The shown pane's content grows the host through CSS within the delivery, and list-detail's own host observer then reports it. That case is not caused by the pass, and the remedy cannot remove it. The fix is the lens's first remedy, which keeps the round-2 operator decision (never write in a delivery). Schedule the pass in one animation-frame callback at most once per frame from the `MutationObserver` and `slotchange`, keep the synchronous pass before a host-set tier change, and record the reading in R-13, data-model and FR-025. The new US3-12 case must be set where the pass is the only writer: one column with the detail shown, the detail's element appending wider content from its own `ResizeObserver`. The README convention should also say that content mutated inside a consumer's `ResizeObserver` can still trigger the browser's loop message through layout alone when the shown layout grows a shrink-to-fit host. |
