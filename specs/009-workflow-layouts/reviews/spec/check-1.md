# Spec check 1

Inputs read: `spec.md`, `checklists/requirements.md`, `.specify/memory/constitution.md` (1.3.1). No earlier check or
fix note exists. Facts checked against `packages/tokens/src/source.ts`: every existing token the spec names exists
with the stated value (`shell-rail-width` 3.25rem, `shell-sidebar-width` 20rem, `gutter` = `space-4` 1rem,
`shell-collapse-sidebar` 45rem, `shell-inspector-width` 19rem, `space-3` 0.75rem, `space-7` 2rem). The frame
arithmetic (876, 1196, 636, 288 px; 54.75, 74.75, 39.75rem), the 848 px five-lane figure and the US3-10 thresholds
are correct. The six new token names are not yet in the source, as expected.

| SPEC-1-01 | blocking | spec.md FR-001, US1-13, US1-9 | FR-001 and US1-13 require that the scroller "clips nothing" in the block direction while it scrolls in the inline direction. In CSS a box whose inline overflow is not `visible` cannot keep the block overflow visible either, so ink overflow of slotted content is clipped on all four sides: the outset focus ring of a focused chip or link at any edge of the strip (and its box shadow) is cut off. The spec covers the scroller's own ring (US1-9) but not the rings of the controls inside it, which is a WCAG 2.4.7 / 2.4.11 risk on the element's main use case (chip rows). As written the requirement cannot be met, and the gap would not be caught. | Restate FR-001/US1-13 as an outcome that can hold: the block size follows the content plus whatever room the slotted controls' focus rings need, and nothing scrolls in the block direction. Add a scenario: a slotted link or button focused at the inline start, the inline end and the block edges of an overflowing and of a fitting scroller shows its whole focus ring (`--ocelle-focus-width` on every side). Add a paired planted defect (scroll box with no room for the ring). |
| SPEC-1-02 | blocking | spec.md FR-013, FR-020, US2-3, US2-8, Edge Cases "Nested scrollers" | Only the lane title is told not to widen the lane (FR-020). Nothing says what a lane does when its slotted content is wider than its share: a card with an unbroken identifier, a wide image, or the nested chip-row scroller of Edge Cases. A flex item's automatic minimum is its content's min-content, so such a lane grows, the equal shares of US2-3 break, and the nested scroller never overflows (it takes its content's size, as in the shrink-to-fit edge case) so its own tab stop never appears. The plan could build either behaviour and the scenarios, which use plain cards, would not tell them apart. | Add to FR-013: a lane's minimum inline size is `--ocelle-lane-min-width`, never its content's min-content; content wider than the lane wraps, scrolls or is clipped inside the lane (say which). Add a scenario with a wide card and with a nested overflowing scroller inside a lane in Frame W: the lanes stay equal within 1 px and the nested scroller is a tab stop. |
| SPEC-1-03 | blocking | spec.md FR-018, FR-019, US2-5, US2-6 | The lane's name rule assumes a title. `label` has no stated default, is not said to be trimmed (unlike `count-label`), and nothing says what the group is named when the label is absent or blank: ", 3", "3", unnamed, or no group role. A host `aria-label` on a lane is not addressed either, though FR-010 settles it for the scroller. The tree outcome of an untitled lane is a tested surface, so the plan would have to guess. | State the lane's `label` default (absent), that it is trimmed, and the name and role when it is absent or blank, with and without `count` (for example: still a group, named by the count alone with no comma, or unnamed). State whether a host `aria-label` decides naming as in FR-010. Add both to US2-6 and to the paired table. |
| SPEC-1-04 | blocking | spec.md FR-025, US3-10, FR-034 | "A CSS length the element can resolve, at its own computed font size" does not define the public attribute's values. US3-10 tests only `rem` and three invalid values. Whether `%` (of what?), `vw`, `cqi`, `calc(...)`, `var(--...)` or a unitless `0` are accepted is open, so two implementations can both pass the scenarios and expose different surfaces (constitution VII). The same holds for the container-tier convention that #8 and #12 are to copy. Also unclear: whether a host that overrides the default token (`--ocelle-list-detail-collapse`) on the element or an ancestor moves the threshold. | List the accepted forms (for example: `px`, `rem`, `em` and unitless `0`; everything else counts as absent) and add one accepted and one rejected example of each excluded kind to US3-10. State whether the default is read from the token's computed value on the element (so a host override applies) or fixed at the token's published value. Carry both into the FR-034 convention. |
| SPEC-1-05 | blocking | spec.md US3-12, FR-025, Edge Cases "Scroller inside a shrink-to-fit host" | In a shrink-to-fit host (US3-12) the element "takes its content's size and chooses its layout from that measured size", but its content's size depends on the layout it chooses: three columns are wider than one. The rule is circular. Depending on content it can settle on either layout or flip on every resize observation (a resize-loop), and the scenario gives no expected layout to test against. | Say what a shrink-to-fit list-detail shows (for example: it measures the width available to it, not its own content-based width; or in a shrink-to-fit host it picks the layout from its widest layout's size, or it holds the one-column layout until a definite size is given), and that the layout does not alternate between frames. Make US3-12's Then name the expected column count for a stated content size. |
| SPEC-1-06 | blocking | spec.md FR-014, US2-9, SC-006 | FR-014 says "a board never makes the page scroll in the inline direction". The board only scrolls inside itself when it has a definite or bounded inline size. The spec says so for the scroller in a shrink-to-fit host (Edge Cases), but a board in a default flex item or table cell takes its lanes' size and widens the page. "Never" cannot be shown by a test and is false in that case. | Bound FR-014 to the case that is tested ("in a block container of definite inline size, such as the frames"), add the board to the shrink-to-fit edge case with its README note, and keep SC-006 as the measured outcome. |
| SPEC-1-07 | note | spec.md US1-3, FR-002 | "Within one animation frame after the resize is observed" leaves open which observation (a resize observer callback, a slot change, a mutation of text inside slotted content) starts the clock. A text change deep in slotted light DOM is not seen by a slot change, only by a size observer on the content. | Name the trigger for each change kind in the plan's contract (`contracts/overflow-region.md`) so the test can wait for it rather than a fixed time. |
| SPEC-1-08 | note | spec.md US1-5, FR-006, FR-009, US1-11 | FR-006 lets the browser's own keyboard scrolling provide the arrow keys, and FR-009/US1-11 require that "nothing animates" under reduced motion. Chromium's native keyboard scrolling may be smooth-animated by a browser setting the element does not control, so "nothing animates" for arrow scrolling is not fully in the element's control. Home, End, PageUp and PageDown on the focused strip, and whether a key pressed at the scroll extent may chain to the page, are not stated. | State what reduced motion means for arrow scrolling (the scroll position reaches its final value within one frame of the key, measured under emulated reduced motion), and state the expected result for Home/End and for an arrow key at the extent. |
| SPEC-1-09 | note | spec.md US1-7, US1-9, FR-005, FR-007 | US1-7 says the fade "fades the content itself toward transparency" and FR-005 that the ring is drawn inside the scroll box and never covered by a fade. A fade that makes the scroll box's own painting transparent at its edges would also fade an inset ring there. The outcomes are fine but they pull against each other; the plan has to show both together. "Fades the content toward transparency" is also close to naming a technique. | Keep the outcome and have the plan test them together: a focused overflowing scroller mid-scroll shows the full ring at both faded edges. Phrase US1-7 as the observable result (the ground behind shows through at the edge) rather than the technique. |
| SPEC-1-10 | note | spec.md US1-12, FR-010, FR-032 "unlabelled" story | An unlabelled overflowing scroller is a tab stop with no role and no name: a screen-reader user lands on an unnamed generic. This is a deliberate choice (an unnamed region is not a landmark) and keeps 2.1.1, and the README is told to require `label`. Recorded so the plan's axe and screen-reader tests assert the exact tree of the "unlabelled" story, not just "no serious finding". | None needed in the spec. The plan's test for US1-12 asserts the node's role and name exactly. |
| SPEC-1-11 | note | spec.md US3-6, FR-028 | Focus moved to the start of a pane lands on a nameless, roleless pane container, so a screen-reader user hears little on the switch unless the host's pane content starts with a heading (README advice, US3-14). "Shows the token focus ring when the change came from the keyboard" depends on the browser's `:focus-visible` heuristic for script focus, since the element cannot see what caused the host to set `detail-open`; US3-6 does not state the ring. | State in FR-028 that the ring follows `:focus-visible` after script focus (the last user input was a key), and add the ring to US3-6 for the keyboard case and its absence for a pointer case. |
| SPEC-1-12 | note | spec.md FR-028, US3-7, Edge Cases "`detail-open` before the element upgrades" | "Upgrading the element moves no focus" and "Focus never stays on a node that has no box" (US3-7) conflict when focus is already inside the list of a server-rendered page whose HTML carries `detail-open` and is one column at upgrade: the list is hidden and focus stays on a node with no box.
