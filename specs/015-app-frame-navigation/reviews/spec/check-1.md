# Spec check 1

| ID | Severity | Where | Finding | Fix |
|----|----------|-------|---------|-----|
| SPEC-1-01 | blocking | spec.md US1.1–3, US2.1–3, FR-001, FR-004, SC-001–003 | SC-001 requires an expected region arrangement for every layout and tier. The spec establishes the wide and narrow personal layouts but gives no personal middle-tier behavior. It names narrow mission navigation without specifying which rail and sidebar destinations remain reachable or how the project layout's narrow navigation differs. Both a drawer that omits the rail and one that includes it could pass the current wording. | State the visible regions, menu availability and drawer contents for every supported combination of layout and tier. Ground the personal behavior in consumer issue #450 and include an assertion that every destination remains reachable in the narrow tier. |
| SPEC-1-02 | blocking | spec.md US1.3, US2.3, US2.4, Edge Cases, FR-004, SC-002 | The focus fallback is underspecified when the menu itself is focused as it disappears, when focus is on a drawer-only control during expansion, and when the target navigation region is empty. Several destinations are allowed without an order. The open-drawer text also closes on any width increase, which would include a resize within the narrow tier. SC-002 allows focus on any visible control, including one unrelated to the user's task. | Define which transition closes the drawer and give ordered focus targets for each control that can disappear. Include keyboard checks for focus on the menu, a destination and the drawer close control, with a fallback when no corresponding destination exists. Assert the selected focus target. |
| SPEC-1-03 | blocking | spec.md FR-002, first Edge Case, SC-001 and Assumptions | The draft gives no observable default threshold pair and names no existing Ocelle contract that supplies it. It also leaves conflicting consumer inputs unresolved if mission 009's property and overrideable token channels are both available. The existing list/detail pair describes layout-specific behavior, so importing its input grammar alone cannot decide what an unconfigured app shell does. | State which defaults apply or cite a concrete contract, and define precedence for the supported consumer input channels, including invalid inputs and an inverted resolved pair. Include fixtures that distinguish default behavior, an override, and fallback. |
| SPEC-1-04 | note | spec.md US1–4 acceptance scenarios and FR-011 | Each story has a priority and an independent test, but several acceptance items read as declarations. For example, the padding scenario omits the step that chooses edges, and the standalone top bar does not say when the host indicates expansion or what the actual control exposes. | Use Given/When/Then conditions for each observable scenario. Include the menu's initial state, activation, and state after the host updates it. Leave event names and payload design for planning. |
| SPEC-1-05 | note | spec.md US3.3, FR-007 and Assumptions | Consumer issue #470 names nav-pill in a primitive list but supplies no destination-specific behavior. The link/current assumption is plausible and documented, but the issue alone cannot substantiate the Desktop V2 claim. | Look for the named consumer's usage or a handoff artifact. Cite evidence for the destination-link behavior if available, or identify the assumption as such and carry it into the plan review. |
| SPEC-1-06 | note | spec.md US2.4, US3.1–4, FR-010–011 | Long text is exercised for the breadcrumb trail. The top bar product name, nav-item label bubble and nav-pill label have no explicit constrained-width cases. No loading or error state is implied by these stateless primitives. | Add constrained-width cases for long translated strings that check readable text, available actions and focus visibility. Use the existing theme, forced-colors and reflow requirements. |
